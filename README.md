# ZeroSol専用 営業・販売・在庫管理プラットフォーム（デモ）

ZeroSol本部の商品・在庫・見積・受注・出荷管理と、販売店の営業支援をつなぐプロトタイプ。表示データ・商品規格・価格は架空です。

## 起動

Node.js 22以上。起動にはAPIキー・DBは不要。PDFエンジンと日本語フォントは配布ファイルに同梱しています。ソースから再ビルドする場合は `npm ci` の後に `npm run build` を実行してください。

```sh
cd /workspace/ZeroSol-home
npm run dev
```

既定ポートは3000。別ポートは `PORT=3002 npm run dev`。検証は `npm test`。

## モード選択

最初に「販売管理」「販売店プラットフォーム」「OEM先」の3モードから選択します。画面右上の「モード選択」で戻れます。選択はタブ内のsessionStorageに保持し、再読込では直前のモードに戻ります。各モードのデータは切り替えても削除しません。

- **販売管理**：在庫・見積・受注・出荷と、顧客からの発注受付を扱うZeroSol向け画面。
- **販売店プラットフォーム**：案件・現場調査・提案・技術相談に加え、自社在庫・補充発注・入荷確認を扱う販売店向け画面。
- **OEM先**：OEM商品・供給条件、見積依頼と、自社在庫・発注・配送・入荷確認を扱うOEM企業向け画面。
- 本部／販売店の表示切替は、モードとは別の設定。会社ごとの在庫・見積データの区別を保ちます。
- 画面と業務メニューを分離する変更であり、本番の認証・アクセス制御の代わりにはなりません。
- 販売管理の見積で関連案件を任意参照できますが、プラットフォームの詳細画面に販売管理の操作は混在させません。

## デモの流れ

1. 「販売管理」モードを選択。初期の表示役割はZeroSol本部。「商品・在庫」で本部倉庫の実在庫・引当済・販売可能数・補充目安を確認。
2. 「入出庫登録」で増減数量と理由を登録。プラスは入庫、マイナスは出庫・棚卸減。
3. 「見積登録」で販売店向け見積の件名・宛先・有効期限・商品明細を登録。税率10%、消費税は小計に対して切り捨て。
4. 見積詳細で「受注登録・在庫引当」。在庫が不足する場合は処理を拒否。
5. 「出荷を記録」で実在庫と引当数を同時に減算。出荷前の受注取消では引当のみ解放。
6. 本部／販売店を切り替えると、在庫と見積は所有者ごとに別表示。一般取引は自動同期しません。下記の顧客発注はブラウザ内で受付・出荷・入荷確認を連携します。
7. 「モード選択」で「販売店プラットフォーム」に切り替えると、案件・現場調査・概算試算・技術相談を利用できます。明細見積の登録は「販売管理」で行います。

本部が販売店の案件と見積を関連付ける場合、顧客情報の共有に同意した案件のみ候補に表示します。案件の進捗変更と受注・出荷記録は独立しており、自動で同期しません。

## 在庫と見積の区別

- メーカー在庫と販売店在庫は別の所有者・倉庫。
- ZeroSol→販売店の見積と販売店→顧客の見積は別の取引。
- 在庫明細の数量単位は巻・缶・台。面積による既存の概算試算から自動転記しない。
- 非在庫の施工費は金額に含めるが、在庫引当の対象外。
- 「概算・提案支援」は参考試算。「見積登録」は明細保存。正式な承認・発行・送信は未実装。
- 出荷済金額は出荷した登録見積の税込合計。会計上の売上や入金額を表すものではない。

## 制限

保存先はブラウザのlocalStorageのみ。認証・サーバー権限・別端末間の会社間連携・メーカー通知・正式見積承認・仕入発注・請求・入金・返品・複数倉庫移動は未実装です。写真は一時プレビューのみで保存されません。役割切替は表示デモでありセキュリティ境界ではありません。複数利用者・タブ間の同時更新に対応しません。実際の顧客情報・在庫・機密情報を入力しないでください。

旧デモの案件データは保持し、追加の販売管理データは別キー `zerosol-sales-v1` に保存します。ブラウザのサイトデータ削除で初期化できます。

本番化では販売店別データ分離、共有同意、監査ログ、商品・取引先マスターの承認、同時更新でも過剰引当しないサーバー側処理が必要です。

## Netlify

`netlify.toml` の公開ディレクトリは `public`。ビルドコマンド・環境変数は不要。更新先はユーザー指定の既存サイト `graceful-cupcake-4152b3.netlify.app`。GitHub連携の場合はmain更新で自動公開。手動デプロイの場合はpublicフォルダを既存サイトにアップロードします。Netlifyの認証情報はこの環境にありません。

## OEM先モード

OEMパートナーAを想定したデモです。供給相談・見積依頼のメモは `zerosol-oem-v1` に保持。発注・配送と自社在庫は下記の顧客取引連携で扱い、同一ブラウザ内のZeroSol側と連携します。旧発注希望メモは履歴として区別して残します。

商品規格・参考ロットは架空。実際のメーカー回答・正式契約・外部通知・配送APIは未接続。OEM企業ごとの認証・専用単価・契約条件・承認・データ分離は本番で実装する必要があります。

## 顧客とZeroSolの取引連携（デモ）

販売店・OEM企業をZeroSolの取引先顧客とする連携です。モードは合計3つのままです。

1. 「販売店プラットフォーム」（初期は販売店ビュー）または「OEM先」で「自社在庫・補充」へ。
2. 保有在庫の確認・入出庫・施工消費を記録。「補充発注」から商品・数量・希望納期を登録。
3. 「販売管理」に切り替えると初期はZeroSol本部ビュー。「顧客発注の受付」で依頼を確認。
発注を登録した時点で、ZeroSolの「受注・出荷」にも「顧客発注・受付待ち」が自動登録されます。価格は「未確定」、在庫は未引当です。「顧客発注の受付」からも同じ依頼を確認できます。
4. 単価と確定出荷予定日を回答し、同じ受注を更新して受付・引当。メーカー在庫不足の場合は受付を拒否。差戻し理由の回答も可能。
5. 受付後に「出荷を記録」。メーカー実在庫と引当を減算。通常の「受注・出荷」にも同じ取引が表示される。
6. 元の顧客モードで配送状況を確認し、「入荷確認」で自社在庫に加算。二重入荷は不可。

メーカー在庫・販売店在庫・OEM先在庫は別管理。顧客の手動出庫はメーカー在庫に影響しません。未受付の依頼のみ顧客が取消可能。出荷済みの取引のみ入荷確認可能。顧客は自社の注文のみ表示し、ZeroSol本部は両チャネルの依頼を受け付けます。

顧客発注と在庫は既存の `zerosol-sales-v1` に保存。既存の案件・見積・入出庫データを保持し、初回利用時にOEM在庫と連携領域を追加します。旧 `zerosol-oem-v1` の見積依頼・発注希望メモも削除せず保持し、旧発注希望は「取引未連携」として区別して表示します。

### 本番との違い

すべて同一ブラウザ内のデモ連携です。別PC・別ユーザーとの同期、実取引の承認、顧客別認証・アクセス制御、メール等の外部送信は未接続。複数端末で使う本番ではサーバーDB、会社単位のアクセス制御、受発注API、同時更新を保護するトランザクション、監査ログ・通知が必要です。分納・返品・配送APIも未実装です。

## 見積書PDF・メール送付

- 見積登録で送付先メール・発行元名・連絡先・住所を入力できます。
- 保存後に日本語A4見積書PDFを自動ダウンロード。宛名、番号、発行日、有効期限、明細、税抜小計、消費税、税込合計、備考を記載します。
- 見積詳細の「見積書PDFを発行」から再発行可能。未確定・取消・差戻し状態では発行できません。
- PDFは印刷ダイアログではなくブラウザ内で生成します。日本語の表示を保つため静的フォントを完全埋め込みしています。PDFは約数MBです。
- 「メール送付」で宛先・文面を確認。「Outlookアプリで作成」はmailtoで既定のアプリを開き、「Gmail画面で作成」はWeb作成画面を開きます。この2方式ではPDFを手動で添付します。送信済みとは記録しません。
- Gmail直接送信はGoogle認証後にPDFを添付します。実送信は下記の設定後のみ有効です。APIが成功を返した場合のみ送信記録を保存し、失敗時は記録しません。API受付は受信者への配達保証ではありません。
- アクセストークンやパスワードをlocalStorageに保存しません。送信元は認証したGmailアカウントです。見積書に登録する発行元メールアドレスは連絡先情報であり、ログイン設定ではありません。

### Gmail直接送信を有効にする管理者設定（未実施）

OutlookアプリでGmailを使う場合も、直接送信の連携先はGmail APIです。

1. Google Cloudでプロジェクトを作成しGmail APIを有効化。
2. OAuth同意画面を設定し、必要に応じてテストユーザーを追加。公開利用ではGoogleの確認手続きが必要になる場合があります。
3. OAuthクライアントを「ウェブアプリケーション」として作成し、承認済みJavaScript生成元に `https://graceful-cupcake-4152b3.netlify.app` を登録。開発用は実際のlocalhostのポートも別途登録。
4. 公開情報のクライアントIDを `public/mail-config.json` の `googleClientId` に設定してデプロイ。クライアントシークレット・パスワード・トークンはこのファイルに絶対に入れない。
5. 送付画面で「Google認証してPDF添付送信」を選び、`https://www.googleapis.com/auth/gmail.send` の許可を与える。認証画面で選択したアカウントから送信されます。

現在の `googleClientId` は空欄です。直接送信は無効で、Googleの実アカウント認証と実送信は未検証。テストはGoogle認証とGmail APIを模擬し、実際のメールは送信していません。
